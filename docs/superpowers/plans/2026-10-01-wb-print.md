# WB sticker and print workflow implementation plan

> **For agentic workers:** Use superpowers:executing-plans for native implementation in this session.

**Goal:** Fix WB empty sticker/429 failures and prepare printable order bundles following wcode's batch, identity, page-order and history workflow.

**Architecture:** Gateway validates fresh WB statuses, requests at most 100 IDs per batch and matches stickers by orderId. A dedicated Windows print service prepares all 58×40 mm pages, publishes PDF and order manifest before printing, and preserves official sticker imagery or its official barcode payload.

**Tech Stack:** .NET 8 WinForms, existing SkiaSharp and ZXing, GitHub Windows CI.

**Spec:** User's WB sticker failure screenshot (0/119), rupphi/test-wcode sticker/export classes at 8f7c3d1ac8598158029b8d037e2d3c128e240727, official WB orders-fbs documentation.

## Global Constraints

- No live order packing or dispatch as a side effect of printing.
- Preserve GS separators and the existing ZXing legacy KIZ encoder.
- Keep Ozon/Yandex official PDF printing behavior.
- Report preparation/spool submission accurately; never claim physical output.

## Review Focus

- Unordered or partial sticker responses must never swap order labels.
- New, cancelled and unknown-status orders must be rejected even if a label was cached.
- Retry delay must respect WB headers and cancellation.
- Missing KIZ for a required order must prevent creation of its complete print bundle.
- Navigation and repeated clicks must not launch duplicate jobs or access disposed controls.
